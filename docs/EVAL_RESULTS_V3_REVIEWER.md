## 3. 关键观察

### 3.1 缺陷检出稳定

5 类注入缺陷全部在两次运行中被打回，且 opinion 给出了可执行修复：

- `unknown_poi`：指出“不存在的测试景点”不在候选池，要求替换；
- `missing_must_visit`：指出漏排“玄武湖景区”，建议替换 Day3 莲花广场；
- `weather_outdoor`：指出连续 3 天中雨 + 全露天，要求室内替代；
- `duplicate_poi`：指出 Day1 重复玄武湖；
- `overpacked`：指出 Day1 5 个景点违反慢节奏习惯，要求减到 2–3 个。

### 3.2 正常对照没有误打回，但提醒质量不合格

clean control 两次都 `approve`，但两次都出现了**错误的开放时间提醒**：

- “Day2中山陵景区和总统府均为周一闭馆，但安排在周日游览，请行前确认”；
- “Day3为周一，建议提前核实中山陵景区和总统府的开放情况”。

实际 fixture 从 2026-08-25（周二）开始，Day2 是周三、Day3 是周四；而且 Reviewer prompt 明确要求“开放时间由 time_check 专项 Agent 核查，你不要评审开放时间”。这说明：

- **verdict 正确 ≠ 提醒正确**；
- clean_block_rate 只统计打回，不统计“通过了但说了错话”；
- 该行为是 `reviewer_issue_precision` 的真实案例，应进入产品修复清单，而不是只当作评测噪音。

### 3.3 挑战集强度有限

5 类缺陷都比较“显眼”：池外景点、漏排点名、全程雨全室外、重复、超上限。它们能验证 Reviewer 是否按规则打回，但**不能证明** Reviewer 能发现更隐蔽的语义问题，例如：

- 老人不能登阶，但路线安排了登阶活动；
- 38°C 正午安排长时间露天暴走；
- 用户隐含排斥商业化，但路线全是商业街区；
- 跨区折返但每个景点单独看都合理。

因此本轮结果应表述为“对 5 类受控注入缺陷 10/10 检出”，不能写成“Reviewer 语义审核准确率 100%”。

## 4. 与 proxy 基线的关系

- proxy 基线（81 条旧 trial）只能看到“首版 L0 非空且返工后修复 6/6”“4/81 WRONG_ACCEPT”，没有 clean_block 与 regression。
- 本轮挑战首次给出真实 `clean_block = 0/2` 与 `k 次一致 = 6/6`，但 n 很小，不能替代 proxy 基线，也不能合并分母。
- 两者回答不同问题：proxy 看历史结果，challenge 看“给定已知缺陷时 Reviewer 是否打回”。

## 5. 边界

- 只有 1 个正常对照；0/2 误打回不足以估计生产 false-positive rate。
- 5 类缺陷都是注入的，不是自然 Planner 失败；不能当自然失败率。
- 同一模型、同一温度；k=2 的一致性不代表独立评委一致性。
- 没有人工逐条判定 opinion 是否正确；本轮只做了关键词与 verdict 检查，3.2 的开放时间错误是人工抽查发现。
- Reviewer 调用会消耗 Token；本轮 32,488 Token 是估算值，不是账单。

## 6. 下一步

1. 把 clean control 扩到 3–5 个，并加入“看似有问题但实际合法”的对照（如周一闭馆景点安排在周二）。
2. 增加 4 类隐蔽语义缺陷：老人登阶、正午暴晒、隐式排斥商业、跨区折返；每类 k=2。
3. 增加 `issue_precision`：人工或规则判断 opinion 是否只指出真实问题，避免“通过但说错话”。
4. 再跑 v3 安全负样本（2 案例 × 3 模式 = 6 trial），得到第一份 SRR/WAR/PARTIAL。
5. 不把本轮 100% 检出写成“Reviewer 准确率 100%”或“误打回率 0%”。
